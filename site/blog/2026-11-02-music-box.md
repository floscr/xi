# Building a music box with Xi

An old Toniebox case, an Arduino Nano, a card reader and an MP3 player: how I built a card-operated music box for my kid with Xi at the bench, and why it ended with a 3D breadboard view, now a public MCP server.

## The box

The idea: put a card on the box and it plays that card's songs; lift it and the music pauses. The case and the ears come from a Toniebox. Inside there's new hardware:

- an **Arduino Nano**, which reads the card and tells the player what to play;
- an **RC522** RFID reader, which identifies cards by their UID, so nothing is written to them;
- a **DFPlayer Mini**: microSD reader, MP3 decoder and a 3 W amplifier in one;
- the Toniebox speaker, and its two ears as volume buttons.

I started from TonUINO, the well-known open-source firmware for exactly this kind of box, and ended up replacing it with a small firmware of my own: a card's UID maps to a folder on the SD card, and that's all.

## One day: firmware, a CLI and a wiring guide

The first day produced more than I expected. With Xi in my dotfiles repo, the agent wrote the firmware with me, and a `toniebox` command-line tool to build it, flash it and read the box's serial log. It also wrote a wiring guide as a single HTML page, with drawings of the breadboard, a table of every wire and a checklist to build and test in order.

![The first prototype on a breadboard: the Nano, the RC522 reader with its antenna, jumper wires, a power bank](/blog/music-box/prototype.jpg)

By the evening there was a small web app, too, to scan cards, link them to songs and flash the SD card. The ears turned the volume up and down with feedback sounds, capped so tiny ears stay safe.

Over the next days the box grew:

- **USB-C power**, so it runs from a charger or a power bank.
- **The SD card over USB**: the DFPlayer doubles as a card reader, so flashing new songs doesn't mean opening the box.
- **A sleep mode**, so a power bank switches itself off.
- **A perfboard to solder it all onto.**
- **On the Raspberry Pi at home**, the web app became a small media centre for the kids. Add a YouTube link there, and it fetches the audio for a card.

![USB-C breakout boards with 5.1 kΩ resistors on the CC pins](/blog/music-box/usb-c.jpg)

## The agent at the bench

The part I liked most: the agent was part of testing, not just of writing code. When I plugged the board in, it read the box's log itself, with a time limit, while I placed a card:

```text
16:54:51 card 49e77512 3     ← reader detects card 3
16:54:51 play 3 1/1          ← DFPlayer plays folder 03, no error
16:54:55 gone                ← lifted, paused
16:54:56 card 49e77512 3
16:54:56 resume              ← same card back, picks up where it stopped
```

I never pasted anything. When I broke an SD card and put in a new one, it found the card on USB and saw it still held another device's files. Halfway through a copy, the DFPlayer dropped off the bus (`error -71`, garbled USB data), and the agent told me to reseat the connection. Then it reformatted the card as FAT32 and flashed it, after checking the kernel log to be sure none of the USB errors had hit the write. When the reader later stopped answering (`err rfid not responding`), it pointed at a loose jumper. The fix was to push the wires back on.

![The Nano and a perfboard, before soldering](/blog/music-box/perfboard.jpg)

## When the drawings stopped helping

The wiring guide's drawings were SVG: correct, but flat. Two things broke them.

First, I soldered the DFPlayer the other way round from the drawing. I asked for a second drawing with the chip turned 180°, and got one, with every moved wire listed in a table.

Then I turned the board over to solder it, and the drawing didn't match what I held anymore: *"it gets really confusing for me that this row is closer to me."* So the agent drew a third version, mirrored, as the underside looks when you flip the board toward you.

![The flat drawing of the breadboard from the wiring guide](/blog/music-box/flat-drawing.jpg)

Three drawings of one board, and each new question would need another. What I wanted was the board itself: something to turn around, to flip, to click a hole and see where it goes.

## From a note to a 3D breadboard

I added a note to my task list: an interactive 3D breadboard view like [BBRouter](https://www.bbrouter.com/), without the simulation, usable both in the chat and in HTML documents like the wiring guide. Then I gave Xi the note.

![The breadboard view: the music box's layout in 3D, with a sidebar of parts and wires](/blog/music-box/breadboard-3d.jpg)

It took a few rounds:

- **A user extension first.** The agent wrote it as plain JavaScript inside a Clojure string. It worked, but that's not how I want code written, so I said so.
- **Squint ClojureScript.** The rewrite has a small library for three.js, written after [threeagent](https://github.com/DougHamil/threeagent): a scene is hiccup, and a re-render reuses the existing objects.
- **An MCP server.** A user extension can't compile squint at load time, so the first version needed a build step. I asked whether it should be an MCP server instead. Now it's a babashka server that compiles its views on demand and works in any host that shows MCP Apps views, not just Xi.

The layout is data: the board, the parts with their pin rows, the wires from hole to hole. The agent writes it, and the view checks it with the same code it draws with, so a wrong hole comes back as an error instead of a missing wire. Then:

- **Click a hole, pin or wire** and everything connected to it lights up.
- **The underside** is one button: the board flips toward you, with every pin dotted and named. That's the drawing I'd asked for.
- **Build steps** put the parts and wires on the board one group at a time, with Prev/Next.
- **The agent can point at things** in an open view: light up the wire it's talking about, or fly the camera there. For anything else it can run squint inside the view and get the value back.

![The underside view: the metal strips that connect the holes, and every soldered pin named](/blog/music-box/underside-3d.jpg)

The wiring guide got the same boards, five in total. Hover over a row of the wire table and its wire lights up; click it and the camera flies there. The perfboard section, which had a side view and a top view, is now one board in three steps: header and socket, then the wires underneath, then the cable plugging on.

![The perfboard at its second step: the wires on the underside, from the reader's header to the Nano's socket](/blog/music-box/perfboard-steps.jpg)

## What I took away

- **Let the agent see the hardware.** A log it can read with a time limit beats pasting output into the chat.
- **Ask for the drawing you need, from where you stand.** "The other way round" and "from below" were five-minute changes. When a format runs out of answers, build the tool.
- **Say what you want early.** The views are squint because I said so after the first version. Moving to an MCP server was one question.

The `breadboard` MCP server is public now, in [xi-extensions](https://github.com/floscr/xi-extensions/tree/main/mcp/breadboard) and on the new [extensions page](/extensions/).
